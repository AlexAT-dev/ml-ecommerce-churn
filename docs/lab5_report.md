# ЛР5. Реліз PoC-системи ChurnGuard (трек 4A)

**Мета.** Перетворити герметичний пайплайн ЛР3 на PoC-сервіс підтримки рішень для менеджера з утримання клієнтів:
* модель у переносному форматі (ONNX);
* реєстр версій (MLflow);
* API з контрактом даних (FastAPI + Pydantic v2);
* OOD-fallback на правило ЛР1;
* трековий модуль 4A — черга розмітки й раунд дорозмітки;
* пояснення (SHAP, LIME) у HITL-дашборді;
* документація (Data Card, Model Card, REFORMS) і чесний ROI.

**Звідки цифри.** Усі числа нижче взято з JSON-звітів у `reports/`. Кожен звіт містить `model_version` і `run_id`:
* **@champion = v2**, run `ed310e5fcd524d249510833a3211ab2b`;
* v1 — run `0e83405cc13b43a982aec9cb94650b3f`, тег `superseded_by = 2`;
* **@challenger = v3**, run `20321913fd5d411cbb95dd43dbe8b660`.

**Відтворення** — послідовність команд у [README → Відтворення ЛР5](../README.md#відтворення-лр5). Уся послідовність повністю перезапускалася
з порожнім реєстром (≈ 17 хв).

## 1. Етап 1. Експорт в ONNX

**Що навчено.**
* v1 — RandomForest із гіперпараметрами ЛР3 (`reports/lab3_final_model.json`): 281 дерево, max_depth 11, `class_weight {0: 50, 1: 118}`, SMOTE під час навчання.
* Перенавчено на train ЛР5 (3 044) у просторі **15 ознак**.
* Ознаки відгуків ЛР2 у сервісі не використовуються: у CRM на момент запиту їх немає, а в ЛР2–3 вони виявились неінформативними.
* Конфігурація препроцесора — `config/generated/config_rf_serving.yaml` (`config_rf_fe` + група клієнтських DFS-ознак).

**Межа графа.**
* **ONNX**: лише `RandomForestClassifier`. Вхід `float_input` [N, 15], виходи `label` і `probabilities` (opset 17, zipmap вимкнено).
* **Поза графом**: `models/preprocessor.skops`. Він містить:
  * 64 клієнтські DFS-ознаки — 56 відношень a/b і 8 логарифмів; їх формули в `src/serving/features.py` збігаються з DFS ЛР2 (0 розбіжностей на train);
  * AdaptiveImputer, OOF-WoE, вінсоризацію, one-hot, SelectKBest(30);
  * `IndexSelector` — 15 колонок, обраних SFS у ЛР3.

  Причина: кастомні трансформери ЛР1–2 не мають конвертерів skl2onnx.
* Семплер SMOTE в експорт не входить: він працює лише під час `fit`.

**Артефакти:**

| Файл | Призначення |
|---|---|
| `models/pipeline.onnx` | граф для сервінгу |
| `models/pipeline.skops` | sklearn-модель — для паритету й SHAP |
| `models/preprocessor.skops` | препроцесинг поза графом |
| `models/shap_background.npy` | фон для пояснень: 300 рядків train у просторі входу ONNX |
| `models/model_meta.json` | контракт: поля запиту, ознаки й dtypes, входи/виходи ONNX, класи, поріг, міра невизначеності, захищені ознаки, правило, версії бібліотек, sha256 ONNX |

**Паритет** (`tests/test_onnx_parity.py`, `reports/onnx_parity_v1.json`):

| Перевірка | Результат |
|---|---|
| test, 1 015 клієнтів | max \|Δp\| = 2.2·10⁻⁷ (atol 10⁻⁴) |
| межі полів Field і всі категорії (синтетика) | у межах atol |
| змін класу після порогу 0.46 | **0**, тож переліку об'єктів біля порогу немає |

**skops: довірені типи** переглянуто вручну. Завантаження йде лише з allowlist префіксів у `src/serving/artifacts.py`:
* `sklearn.tree._tree.Tree`;
* власні трансформери `src.*`;
* `f_classif`;
* `KDTree` і `EuclideanDistance64` (OOD).

Повний перелік — у README.

* параметри моделі й препроцесингу;
* теги — DVC-хеші (`dvc_train_md5`, `dvc_holdout_md5`, `dvc_raw_md5`) і `release`;

  | Оцінка | ROC-AUC | F1 | Втрати, у.о./клієнта |
  |---|---|---|---|
  | вкладена CV ЛР3 (95% t-інтервал по 5 зовнішніх фолдах) | 0.918 [0.885; 0.950] | 0.666 [0.603; 0.728] | 69.0 [67.2; 70.7] |
  | test (бутстреп 1 000) | 0.907 [0.880; 0.928] | 0.659 [0.601; 0.711] | 69.0 [60.9; 77.1] |

* артефакти: ONNX-модель (`mlflow.onnx.log_model`, зареєстрована як `ChurnGuard`) і serving-файли, зокрема `pipeline.skops` — **в одному run**;
* `deploy/requirements.txt` — зафіксовані версії.

**Перевірка:** `mlflow.onnx.load_model("models:/ChurnGuard@champion")` завантажує граф з реєстру.

**Аліаси замість Stages.**
* v1 → @champion.
* Після етапу 4: v2 → @champion, у v1 — тег `superseded_by = 2`.
* Відкат — перепризначення аліасу без зміни коду: сервіс резолвить аліас у lifespan.

**Стратегія виведення:**
1. **Shadow** — challenger отримує копію запитів, його прогнози лише логуються.
2. **Канарка** на частині менеджерів.

A/B на клієнтах не застосовуємо: рішення ухвалює людина, а ефект пропозиції видно через місяць. Помилкова версія встигла б
зачепити багатьох клієнтів раніше, ніж це стане помітно.

## 3. Етап 3. FastAPI-сервіс і контракт Pydantic v2

**Архітектура** (`src/app/main.py`) — три шари:
1. HTTP: ендпоінти і схеми;
2. сервіс: `src/serving/predictor.py` — препроцесор → ONNX → OOD → правило;
3. артефакти: MLflow @champion або `models/`.

**Lifespan:**
* завантажує модель один раз;
* виконує **`check_contract`**: поля запиту = `request_fields`, входи ONNX і їх ширина, вихід препроцесора = `features`
  (і склад, і порядок), класи, відсутність захищених ознак у запиті, run_id;
* поки артефакти не завантажено або контракт порушено, `/health` = **503**.

Ендпоінти з інференсом — звичайні `def`: FastAPI виконує їх у threadpool, тож event loop не блокується.

**Контракт** (`src/app/schemas.py`):
* `PredictionRequest` — `strict`, `extra="forbid"`;
  * межі `Field` — доменні діапазони ЛР1;
  * `Literal` для категорій;
  * `Optional` для полів із природними пропусками;
  * валідатор `CouponUsed ≤ OrderCount`.
* `CityTier` або `Gender` у запиті → **422**.
* Помилки мають єдиний формат `{"error": {"code", "message", "details"}}`.

| Ендпоінт | Що робить |
|---|---|
| `GET /health` | 503 / 200, версія моделі, run_id, наявність OOD |
| `POST /v1/predict` | `score`, `label`, `uncertainty`, `meta {model_version, fallback_applied, ood_log_density}` |
| `POST /v1/predict_batch` | до **256** запитів; понад ліміт — 422 |
| `POST /v1/feedback` | `y_true` за `request_id`; невідомий id — 404 |
| `POST /v1/explain` | прогноз + SHAP + LIME + узгодженість |
| `GET /v1/model`, `GET /v1/label_queue` | метадані моделі; черга розмітки (трек 4A) |

**Невизначеність** — ентропія прогнозу, міра ЛР4A: H(p) = −p·log₂p − (1−p)·log₂(1−p) ∈ [0, 1].

**Журнал:** кожен запит логується в SQLite (`feedback.db`) — і ознаки, і прогноз.

## 4. Етап 4. OOD-fallback, фідбек, автотести, трековий модуль

### 4.1. OOD-детектор (`src/app/ood.py`)

**Побудова:**
* Простір — вхід ONNX (15 ознак).
* StandardScaler → PCA(whiten). Кількість компонент — найменша, що пояснює ≥ 0.9 дисперсії: **k = 9 (0.919)**.
  Обмеження ТЗ «не більше 10» виконано.
* KDE (gaussian) на 80% train. Bandwidth **0.233** обрано GridSearchCV за log-likelihood (KFold 5). Сітка розширюється, якщо оптимум лежить на межі.
* Поріг **−36.2** — 1-й перцентиль log-густини на відкладених 20% train.

**Перевірка на test** (`reports/ood_report.json`):

| Показник | Значення |
|---|---|
| Частка fallback (хибні спрацювання на типових даних) | **0.1%** (1 з 1 015) |
| Виявлено штучних OOD: test, зсунутий на 3σ по PC1 | **76%** |
| … по PC1 + PC2 | **87%** |
| Система (модель + правило) vs лише модель | однакові рішення: для єдиного OOD-клієнта правило й модель збіглися |

* Частка fallback нижча за орієнтир 1–3%. Детектор консервативний: він рідко перериває модель, зате пропускає частину зсунутих точок
  (76–87%). Перегляду ТЗ вимагає лише частка, помітно більша за 3%.
* **На реальних нетипових запитах якість детектора не оцінено**: таких міток немає.

**Перша версія детектора мала відхилення від ТЗ, яке виправлено.** Спочатку кількість компонент була обмежена 6 (0.81 дисперсії).
Це не відповідало правилу ТЗ, тому v1/v2 перереєстровано з k = 9. Для порівняння, з k = 6 було б:

| | Fallback на test | Виявлено OOD (PC1 / PC1+PC2) |
|---|---|---|
| k = 6 (відхилення від ТЗ) | 0.5% | 85% / 91% |
| **k = 9 (правило ТЗ)** | **0.1%** | **76% / 87%** |

Розмірність обрано за правилом ТЗ, а не за цими показниками: густини в просторах різної розмірності непорівнянні.

**Реєстрація v2.** Run `release-v2` містить той самий ONNX, `models/ood/ood.skops` і `model_meta.json` з блоком `ood`.
Аліас @champion перепризначено на v2, у v1 — тег `superseded_by = 2`. Lifespan завантажує OOD-компоненти разом із моделлю.

### 4.2. Трековий модуль 4A — цикл розмітки

1. **Потік** (`label_round --stream`): пул (1 015) пройшов через `/v1/predict` без міток. Мітки пулу — «оракул»
   (`data/processed/pool_oracle.csv`, не в git).
2. **Черга** (`src/observability/label_queue.py` → `reports/label_queue.csv`):
   * беруться запити з журналу без фідбеку;
   * стратегія ЛР4A **entropy + diversity**: топ-100 за ентропією → KMeans(20) → найближчий до кожного центру;
   * результат — 20 запитів, ентропія 0.946–1.000.
   * **3 OOD-запити** пулу (`fallback_applied = true`) у чергу не потрапили: вони виведені окремо (`reports/label_queue_ood.csv`),
     бо сигналізують про нову зону даних, а не про межу класів.
3. **Розмітка** (`--label`): 20 міток оракула через `/v1/feedback`. У дашборді те саме робиться вручну у вкладці «Черга розмітки».
4. **Перенавчання** (`--retrain`):
   * train + 20 розмічених, ті самі гіперпараметри, той самий експорт і тест паритету (0 змін класу) → **v3 @challenger**;
   * теги: `strategy = entropy_diversity`, `n_new_labels = 20`, `parent_champion = 2`;
   * базова лінія — модель, дорозмічена 20 **випадковими** запитами з того самого пулу (не реєструється).
5. **Порівняння на test** — парний бутстреп, 1 000 повторень, однакові індекси для всіх моделей (`reports/label_round.json`):

| Модель | ROC-AUC | F1 | Втрати, у.о./клієнта |
|---|---|---|---|
| champion v2 | 0.9067 | 0.659 | 69.01 |
| challenger v3 (черга) | 0.9086 | 0.642 | 69.59 |
| random (20 випадкових) | 0.9105 | 0.641 | 69.64 |

| Різниця (95% CI) | ROC-AUC | F1 | Втрати |
|---|---|---|---|
| challenger − champion | +0.0019 [−0.0043; 0.0083] | −0.016 [−0.040; 0.009] | +0.58 [−0.28; 1.43] |
| random − champion | +0.0038 [−0.0033; 0.0126] | −0.018 [−0.043; 0.006] | +0.63 [−0.20; 1.51] |

**Рішення: @challenger НЕ просунуто.** Усі інтервали містять 0, тож перевагу не доведено. @champion автоматично не змінюється.

Чому покращення немає: 20 міток — це 0.7% train. Ефект active learning у ЛР4A проявлявся при 150–450 мітках, а не поверх повної вибірки.

## 5. Етап 5. XAI-шар і дашборд

**Локальні пояснення** (`src/xai/explain.py`, `POST /v1/explain`):
* **SHAP** `TreeExplainer` на `pipeline.skops` з того самого run, що й ONNX:
  * функція цінності **interventional** з фоном `shap_background.npy` (300 рядків train);
  * вихід — імовірність класу 1, base value 0.231.
* **LIME** `LimeTabularExplainer(training_data=фон)`, 1 500 збурень, на сервері (не через `/v1/predict_batch`).
* У відповіді — узгодженість SHAP і LIME: спільних у топ-5 і ρ Спірмена.

**Офлайн-звіт** (`src/xai/offline_report.py` → `reports/xai/`, залоговано в run @champion):

| Що | Результат |
|---|---|
| SHAP summary (beeswarm) на test | топ-3: скарга, стаж, Tenure / OrderCount |
| PDP або ALE для двох найважливіших ознак | `Complain` — PDP + ICE (max \|ρ\| з іншими 0.10); `Tenure` — **ALE**, бо ρ = 0.96 з `TenureStage`, і PDP усереднював би по нереалістичних комбінаціях |
| Сурогатне дерево (глибина ≤ 4, на ймовірностях моделі) | fidelity R² = 0.82 на test |
| Стабільність: 30 об'єктів × 20 збурень (шум 3% std, лише неперервні поля, обрізання до Field, усі проходять валідацію) | ρ Спірмена топ-5 = 0.95; збіг топ-5 = 0.91 |

Стабільність і збіг SHAP з LIME — **діагностика надійності, а не доказ правильності**. Внески SHAP — в одиницях імовірності;
це не відсотки й не причини.

**Дашборд** (`src/dashboard/app.py`, Streamlit) працює лише через API:

| Вкладка | Вміст |
|---|---|
| Інференс і пояснення | форма запиту без захищених ознак; ризик, рекомендація, невизначеність; попередження про OOD; waterfall і LIME |
| Глобальні пояснення | beeswarm, PDP/ALE з обґрунтуванням вибору |
| Довіра до пояснень | fidelity сурогату, стабільність, текст дерева |
| Черга розмітки | таблиця черги, пояснення обраного запиту, форма `y_true` → `/v1/feedback`, лічильник, OOD окремо, порівняння champion / challenger / random з інтервалами |

## 8. Обмеження

* Розмітку симульовано: оракул не помиляється й нічого не коштує. Раунд із 20 мітками не дав доведеного покращення.
* Матриця втрат і сценарії ROI — експертні припущення; ефект наведено діапазоном.
* CityTier 2 (n = 32) — оцінки справедливості ненадійні.
* OOD-детектор перевірено лише на штучних зсувах; частка fallback 0.1% — нижче орієнтиру.
* Сервіс однопроцесний, з SQLite. Це PoC, а не продакшен: немає автентифікації, черги задач і моніторингу дрейфу (трек 4B).
